[[fbcrypt-client-app]]
= Как работает шифрование Firebird на стороне клиента

== Способы передачи ключа

Клиент может передать ключ серверу несколькими способами. Выбор зависит от типа приложения:

[cols="2,3,2", options="header"]
|===
| Способ | Для каких приложений | Обмен ключом защищён
| Библиотека `fbcrypt` (<<fbcrypt-client-native>>)
| Нативные приложения с исходным кодом (Delphi, Lazarus, C++ и др.)
| Да

| Библиотека `KeySource` (<<fbcrypt-keysource>>)
| Нативные приложения без исходного кода
| Да

| Плагин `KeyHolderStdin` (<<fbcrypt-utils>>)
| Утилиты командной строки Firebird
| Да

| Запрос ключа у пользователя (<<fbcrypt-client-prompt>>)
| Приложения без исходного кода, когда ключ вводит человек
| Да

| Свойство подключения драйвера (<<fbcrypt-client-java>>, <<fbcrypt-client-net>>)
| Java (Jaybird), .NET
| Нет. Нужны `UnsafeClient = true` и шифрование протокола
|===

== Нативные приложения

Чтобы понять, что происходит, когда клиентское приложение подключается к зашифрованной базе данных, рассмотрим обычный процесс подключения к незашифрованной базе данных для нативных приложений.

Обратите внимание: здесь и далее под "`нативным`" подразумевается приложение, устанавливающее сетевое соединение с сервером с помощью `fbclient.dll`; обычно такие приложения создаются на Delphi, C++, PHP. В отличие от нативных приложений, Java и .NET реализуют свои собственные версии протокола, которые будут рассмотрены ниже.

Процесс подключения:

. Клиентское приложение загружает клиентскую библиотеку
.. `fbclient.dll` – нативные приложения Windows
.. `libfbclient.so` – нативные приложения Linux
. Клиентское приложение инициирует соединение, отправляя
.. Имя пользователя, например, SYSDBA
.. Пароль, например, masterkey
.. Путь/псевдоним базы данных

В случае зашифрованной базы данных требуется дополнительный шаг: необходимо передать имя ключа шифрования и его значение.

Важно отметить, что передача ключа должна выполняться до обычного соединения, поскольку страницы данных с метаданными, включая имя владельца базы данных, кодировку и т. д., зашифрованы.

Таким образом, это приводит нас к следующему:

. Необходим дополнительный сетевой обмен данными для передачи ключа до обычного соединения.

. Передача ключа из клиентского приложения в Firebird требует написания кода с использованием асимметричного шифрования и реализации интерфейса обратного вызова, что может быть довольно сложным. Для упрощения этой задачи разработчики плагинов предоставляют пример кода для подключения или, как в рамках плагинов IBSurgeon, создают дополнительную библиотеку `fbcrypt.dll`/`libfbcrypt.so`, которая реализует простой в использовании подходящий интерфейс для передачи ключей из клиентского приложения.

=== Функции библиотеки fbcrypt

Библиотека `fbcrypt.dll`/`libfbcrypt.so` экспортирует три простых функции, которые следует вызывать перед тем как ваше приложение установит соединение с базой данных:

[source,cpp]
----
int fbcrypt_init(const char* clientPathName);
int fbcrypt_key(const char* name, const unsigned char* data, unsigned dl);
int fbcrypt_callback(void* provider);
----

На Windows функции используют соглашение о вызовах `stdcall`, на Linux -- `cdecl`.

`fbcrypt_init`::
Загружает клиентскую библиотеку Firebird по указанному пути и *очищает список ключей*, сохранённых ранее.
+
* Повторный вызов с тем же путём допустим.
* Повторный вызов с другим путём возвращает ошибку: в одном процессе `fbcrypt` работает только с одной клиентской библиотекой.
* Вызов с `NULL` (`nil`) только очищает список ключей. Используйте его, чтобы заменить ключи.

`fbcrypt_key`::
Добавляет в список именованный ключ: имя, значение и длину значения в байтах.
+
* Функцию можно вызвать несколько раз, чтобы добавить несколько ключей.
* Имя ключа -- строка с завершающим нулём, не длиннее 255 байт. Регистр букв в имени не учитывается.
* Длина ключа -- 16, 24 или 32 байта (см. <<fbcrypt-keygen>>).

`fbcrypt_callback`::
Регистрирует в клиентской библиотеке обратный вызов, который передаёт серверу ключи из списка.
+
* Если приложение использует объектно-ориентированный API, передайте указатель на провайдер (`IProvider`), через который создаются подключения.
* Если приложение использует ISC API (`isc_attach_database`), передайте `NULL` (`nil`). В этом случае обратный вызов регистрируется *для текущего потока*.

Все функции возвращают `0`, если функция выполнилась без ошибок, и значение `< 0` в противном случае.

Коды ошибок:

fbcrypt_init::
* `-1` клиентская библиотека с указанным именем не может быть загружена, либо библиотека уже была загружена по другому пути.
fbcrypt_key::
* `-1` неизвестная ошибка сохранения ключа, возможно нехватка памяти.
fbcrypt_callback::
* `-10` клиентская библиотека не была загружена с помощью `fbcrypt_init`;
* `-5` в библиотеке, загруженной с помощью `fbcrypt_init`, отсутствует вызов `fb_get_master_interface` или `fb_database_crypt_callback` - как правило очень старый (\<=2.5) `fbclient` или вообще "не та" библиотека;
* `-1` неизвестная ошибка регистрации сохранённых ключей в `fbclient` - обычно не возникает.

[IMPORTANT]
====
Приложение должно использовать `fbclient.dll` из клиентского пакета плагина шифрования и ту же самую библиотеку, путь к которой передан в `fbcrypt_init`. Если компонент доступа загрузит другой экземпляр `fbclient.dll`, обратный вызов будет зарегистрирован не в той библиотеке, и ключ передан не будет.

Разрядность `fbcrypt.dll`, `fbclient.dll` и приложения должна совпадать (32 или 64 бит).
====

=== Пример

Для подключения нативного приложения (использующего `fbclient.dll`) к зашифрованной базе данных необходимо выполнить 3 вызова. Ниже приведен пример на Delphi (упрощенный, без обработки ошибок).

Объявление функций:

[source,pascal]
----
function fbcrypt_init(clientPathName: PAnsiChar): Integer; stdcall;
  external 'fbcrypt.dll';
function fbcrypt_key(name: PAnsiChar; data: PByte; dl: Cardinal): Integer; stdcall;
  external 'fbcrypt.dll';
function fbcrypt_callback(provider: Pointer): Integer; stdcall;
  external 'fbcrypt.dll';
----

В обработчике события `BeforeConnect`:

[source,pascal]
----
const keyRed: array [0..31] of byte  = ($ec,$a1,$52,$f6,$4d,$27,$da,$93,$53,$e5,$48,$86,$b9,$7d,$e2,$8f,$3b,$fa,$b7,$91,$22,$5b,$59,$15,$82,$35,$f5,$30,$1f,$04,$dc,$75);

fbcrypt_init(PAnsiChar('C:\Firebird30\fbclient.dll'));
fbcrypt_key(PAnsiChar('RED'), @keyRed, SizeOf(keyRed));
fbcrypt_callback(nil);

 // Then connect as usual
Database1.Active:=True;
----

[WARNING]
====
В примере ключ записан в коде как константа. Так делать можно только в учебных примерах: константу легко найти в исполняемом файле. В рабочем приложении получайте ключ из защищённого хранилища или собирайте его во время работы программы.

=== Несколько ключей и несколько баз данных

Список ключей `fbcrypt` один на весь процесс. При каждом подключении серверу передаются *все* ключи из списка. Сервер выбирает нужный по имени ключа, которое записано в заголовке базы данных.

Поэтому для работы с несколькими базами данных достаточно дать ключам разные имена и добавить их все:

[source,pascal]
----
fbcrypt_init(PAnsiChar(ClientLibPath));
fbcrypt_key(PAnsiChar('RED'), @keyRed, SizeOf(keyRed));
fbcrypt_key(PAnsiChar('GREEN'), @keyGreen, SizeOf(keyGreen));
fbcrypt_callback(nil);
----

Чтобы заменить ключи, очистите список вызовом `fbcrypt_init(nil)` и добавьте новые ключи. Ключи остаются в памяти до следующего вызова `fbcrypt_init` или до выгрузки `fbcrypt.dll`. Отключение от базы данных список не очищает.

=== А как насчет потокобезопасности в случае многопоточных клиентских приложений?

Позвольте напомнить вам несколько общих моментов реализации многопоточных клиентских приложений.

Начиная с Firebird 2.5, несколько потоков внутри приложения могут безопасно использовать одно подключение к базе данных, поскольку вся необходимая синхронизация выполняется внутри `fbclient.dll`.

Однако в этом случае потоки смогут работать с подключением только по очереди.

Это приемлемо для приложений, которые не требуют высокопроизводительного обмена данными с базой данных — если ожидание выполнения SQL-запроса одним потоком, пока другой поток выполняет другой SQL-запрос, не является проблемой, проще использовать простую модель, когда одно подключение используется несколькими потоками.

Если приложение требует параллельного выполнения SQL-запросов (т.е. это полномасштабное клиентское приложение), лучше использовать отдельное подключение к БД для каждого потока.

Ситуация с обменом ключами для подключений к зашифрованным базам данных несколько сложнее.

При каждом подключении клиентская библиотека передает ключи от клиента, но это не связано напрямую с потоками в клиентском приложении, ситуация зависит от используемого API.

Как известно, клиентская библиотека Firebird, начиная с версии 3.0, предлагает 2 типа API: новый объектно-ориентированный API, основанный на концепции провайдеров, и устаревший isc_ API, реализованный в качестве обходного пути для поддержания совместимости со старыми драйверами Firebird.

Если используется новый объектно-ориентированный клиентский API, достаточно создать провайдер, предоставить ему необходимые ключи (`fbcrypt_callback(provider)`), а затем использовать его для новых подключений из любых потоков.

Если используется клиентский isc_ API, для каждого подключения клиентская библиотека будет создавать свой собственный временный провайдер, который не виден и недоступен для конечного пользователя.

В этом случае обратный вызов берётся из потока, где вызывается `isc_attach_database`: клиентская библиотека хранит указатель на него в локальном хранилище потока.

*На практике многие библиотеки доступа используют isc_ API (например, FireDAC). Для них необходимо вызывать `fbcrypt_callback(nil)` в каждом потоке, который подключается к зашифрованной базе данных, до установления соединения.* Объектно-ориентированный API используют, например, IBX для Lazarus и `firebird-driver` для Python.

Правила для многопоточного приложения:

[cols="2,3", options="header"]
|===
| Функция | Где вызывать
| `fbcrypt_init(путь)`
| Один раз при запуске приложения. Функция очищает общий список ключей, поэтому не вызывайте её, пока другие потоки подключаются к базе данных.

| `fbcrypt_key(...)`
| После `fbcrypt_init`, один раз для каждого ключа. Список ключей общий для всех потоков и защищён от одновременного доступа.

| `fbcrypt_callback(nil)` (isc_ API)
| В каждом потоке, который устанавливает соединение, до подключения. Одного вызова на поток достаточно.

| `fbcrypt_callback(provider)` (объектно-ориентированный API)
| Один раз для каждого провайдера.
|===

При использовании пула подключений (isc_ API) помните: новое физическое подключение создаёт тот поток, который запросил его у пула. Вызывайте `fbcrypt_callback(nil)` в каждом рабочем потоке.

Значения ключей должны быть установлены до установления соединения; после подключения значение ключа изменить нельзя.

[[fbcrypt-keysource]]
== Legacy приложения без исходных кодов

Что если вы хотите использовать шифрование базы данных, но для вашего приложения нет исходных кодов? Мы предусмотрели такую ситуацию. В этом случае вам необходимо создать динамическую библиотеку с именем `KeySource.dll` и положить её рядом с `fbclient.dll`.

=== Как это работает

. Приложение не регистрирует обратный вызов для передачи ключа.
. При подключении `fbclient` читает параметр `KeyHolderPlugin` из своего файла `firebird.conf` и загружает плагин `KeyHolder` из каталога `plugins`.
. Плагин `KeyHolder` ищет библиотеку `KeySource` в каталоге библиотек Firebird, вызывает её функцию `MakeKeys` и получает ключи.
. `KeyHolder` на клиенте передаёт ключи плагину `KeyHolder` на сервере по защищённому протоколу.

Код приложения менять не нужно.

=== Какие файлы нужны

В каталоге, из которого приложение загружает `fbclient.dll`, должны находиться файлы из клиентского пакета (`Client\32bit` или `Client\64bit`):

[listing]
----
fbclient.dll            клиентская библиотека из пакета плагина
firebird.conf           содержит строку KeyHolderPlugin = KeyHolder
firebird.msg
libcrypto-*.dll         библиотека OpenSSL
KeySource.dll           ваша библиотека с ключами
plugins\keyholder.dll   плагин управления ключами
... остальные dll из каталога пакета
----

[cols="1,3", options="header"]
|===
| Платформа | Имя и расположение библиотеки `KeySource`
| Windows | `KeySource.dll` рядом с `fbclient.dll`
| Linux | `libKeySource.so` в каталоге библиотек Firebird (обычно `/opt/firebird/lib`)
|===

Разрядность файлов (32 или 64 бит) должна совпадать с разрядностью приложения, а не операционной системы.

=== Функция MakeKeys

Библиотека должна экспортировать одну функцию с соглашением о вызовах `cdecl`:

[source,cpp]
----
char* MakeKeys(char* (*allocator)(unsigned int size), unsigned int* size);
----

Правила:

* Память для текста с ключами выделяйте только функцией `allocator`, которую передаёт плагин. Плагин сам освобождает эту память.
* В `*size` запишите длину текста в байтах без завершающего нуля. Функция `allocator(n)` выделяет `n + 1` байт.
* Функция возвращает указатель на выделенный буфер. Если вернуть `NULL`, плагин возьмёт ключи из файла `KeyHolder.conf`.

Код динамической библиотеки `KeySource.dll` тривиален.

Пример на языке C/C++:

[source,cpp]
----
#include <stdio.h>
#include <string.h>

const char* keys =
"Key=Zero 0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,\n"
"Key=White 0x25,0x83,0x46,0x88,0xf4,0x1d,0x2c,0x69,0x48,0x53,0x7a,0x4a,0x0a,0x15,0x35,0x22,0x2c,0x02,0x4f,0x65,0xb8,0x73,0x77,0x07,0x89,0xb2,0xc6,0x04,0xda,0xe4,0x03,0x5d,\n";

extern "C" char* MakeKeys(char* (*allocator)(unsigned int size), unsigned int* size)
{
	*size = strlen(keys);			// store keys length
	char* rc = allocator(*size);	// allocate memory for keys data
	memcpy(rc, keys, (*size) + 1);	// store keys data

	return rc;
}
----

=== Формат текста с ключами

Функция `MakeKeys` возвращает сразу несколько именованных ключей. Текст имеет тот же формат, что и файл `KeyHolder.conf`: один ключ в строке, строки разделяются переводом строки.

[source]
----
<keys> ::= <key-line> \n [ <key-line> \n ... ]

<key-line> ::= Key=<KeyName> <key_value>
             | Password=<KeyName> <passphrase>

<key_value> ::= 0x<hex-pair>,[0x<hex-pair>,...]
----

У каждого ключа есть имя, которое записывается после `Key=`. Далее после пробела следует сам ключ. Каждый байт записывается как шестнадцатеричная пара с префиксом `0x`. Байты отделяются запятой без пробелов. Подробнее о формате см. <<fbcrypt-keygen-format>>.

[NOTE]
====
Если библиотека `KeySource` найдена и вернула ключи, строки `Key` и `Password` из файла `KeyHolder.conf` не используются. Остальные параметры этого файла (`UnsafeClient`, `Prompt`) продолжают действовать.
====

[WARNING]
====
Библиотека `KeySource.dll` из клиентского пакета содержит только тестовые ключи. Для рабочей системы соберите собственную библиотеку.

Ключ находится внутри `KeySource.dll` на рабочей станции. Этот способ защищает файл базы данных и резервные копии при краже. Он не защищает от пользователя, который имеет полный доступ к рабочей станции и может скопировать библиотеку.
====

[[fbcrypt-client-prompt]]
== Запрос ключа у пользователя

Плагин `KeyHolder` на стороне клиента может сам запросить ключ у пользователя. В файле `firebird.conf` клиента должна быть строка `KeyHolderPlugin = KeyHolder`. Добавьте в файл `plugins/KeyHolder.conf` параметр `Prompt` с текстом приглашения:

[source,conf]
----
Prompt = Enter key %k for database %d
----

В тексте можно использовать подстановки:

[cols="1,3", options="header"]
|===
| Подстановка | Значение
| `%k` | имя ключа из заголовка базы данных
| `%d` | имя базы данных
| `%%` | символ `%`
|===

Как это работает:

. Приложение подключается к зашифрованной базе данных, ключ не найден.
. Плагин показывает окно ввода (Windows) или запрашивает ввод в терминале (Linux).
. Если введённый текст имеет формат `0x..,0x..,`, он используется как ключ. Иначе текст считается парольной фразой, и ключ вычисляется из неё (см. <<fbcrypt-keygen-password>>).
. Подключение повторяется. При ошибке плагин показывает её текст и запрашивает ключ снова.
. После успешного подключения ключ хранится в памяти процесса до его завершения.

Запрос показывает клиент. Сервер Firebird ключ у пользователя не запрашивает.

Проверено на Windows при обычном подключении к серверу: Firebird 3.0, 4.0, 5.0. В режиме embedded с настройкой `Providers = Engine13` окно ввода в проверке не появилось: для embedded используйте библиотеку `KeySource`.

[[fbcrypt-client-java]]
== Java-приложения

Драйвер Java (JayBird) имеет собственную реализацию (на чистом Java) протокола Firebird. Jaybird 4 (и 3.0.4+) добавляет поддержку коллбэков шифрования базы данных Firebird 3 в реализации протокола версии 13 на чистом Java.
Из файла https://www.firebirdsql.org/file/documentation/drivers_documentation/java/4.0.2/release_notes.html#database-encryption-support[Readme Jaybird 4]:

[quote]
____
Текущая реализация проста и поддерживает только ответ со статическим значением из свойства соединения. Имейте в виду, что ответ со статическим значением для шифрования базы данных не очень безопасен, так как он может легко привести к атакам повторного воспроизведения или непреднамеренному раскрытию ключа.

В будущих версиях Jaybird (вероятно, 5) будет добавлена ​​поддержка плагинов шифрования базы данных, требующих более сложного коллбэка.
____

Возможности более новых версий Jaybird уточняйте в их release notes.

На практике это означает, что нам нужно установить значение для коллбэка шифрования (имя ключа и значение ключа через двоеточие) в свойстве соединения `dbCryptConfig`.

Формат значения:

[source]
----
<KeyName>:<key_value>[:<KeyName>:<key_value>...]

<key_value> ::= 0x<hex-pair>,[0x<hex-pair>,...]
----

Например:

[source,java]
----
String url = "jdbc:firebirdsql://localhost/g:/Databases/ODS12/crypt.fdb?lc_ctype=utf8"
    + "&dbCryptConfig=MyKey:0xec,0xa1,0x52,0xf6,0x4d,0x27,0xda,0x93,0x53,0xe5,0x48,0x86,0xb9,0x7d,0xe2,0x8f,0x3b,0xfa,0xb7,0x91,0x22,0x5b,0x59,0x15,0x82,0x35,0xf5,0x30,0x1f,0x04,0xdc,0x75,";
----

Лучше передавать ключ не в URL, а в свойствах подключения. Тогда ключ не попадёт в журналы, где печатается URL:

[source,java]
----
Properties props = new Properties();
props.setProperty("user", "SYSDBA");
props.setProperty("password", "masterkey");
props.setProperty("dbCryptConfig", "MyKey:" + keyHex);
Connection con = DriverManager.getConnection(
    "jdbc:firebirdsql://localhost/g:/Databases/ODS12/crypt.fdb", props);
----

Также можно указать строку в формате base64 — из файла readme:

[quote]
____
Строки с префиксом `base64:` остальная часть строки декодируется как base64 в байты.
Символы заполнения "=" необязательны, но если они присутствуют, то должны быть допустимыми (то есть, если вы используете заполнение, вы должны использовать правильное количество символов заполнения для длины).
Если закодированное в base64 значение содержит "+", оно должно быть экранировано как %2B в URL-адресе JDBC. Для обратной совместимости с Jaybird 3 мы не можем переключиться на URL-безопасный вариант base64.
____

В base64 кодируется вся строка `MyKey:0xec,0xa1,...`, а не двоичное значение ключа.

[[fbcrypt-client-unsafe]]
=== Параметр UnsafeClient

При таком способе драйвер не выполняет защищённый обмен, описанный в <<fbcrypt-server>>. Он отправляет ключ серверу как есть. Если шифрование сетевого протокола не включено, ключ легко перехватить анализатором сетевого трафика, таким как WireShark.

Поэтому плагин `KeyHolder` от IBSurgeon по умолчанию не принимает такие ключи. Чтобы разрешить передачу ключей этим способом:

. Установите параметр `UnsafeClient = true` в файле `plugins/KeyHolder.conf` на сервере.
. Включите обязательное шифрование протокола: `WireCrypt = Required` в `firebird.conf` на сервере.
. Используйте аутентификацию `Srp` или `Srp256`. Плагин `Legacy_Auth` не создаёт сеансовый ключ, и шифрование протокола с ним не работает.

[source,conf]
----
# plugins/KeyHolder.conf
UnsafeClient = true
----

[source,conf]
----
# firebird.conf
WireCrypt = Required
----

[[fbcrypt-client-net]]
== Приложения .NET

Провайдер Firebird.NET реализует аналогичную схему обмена ключами для зашифрованных баз данных и также требует установки параметра `UnsafeClient=true` в файле `KeyHolder.conf` (см. <<fbcrypt-client-unsafe>>).

Пример строки подключения для зашифрованных баз данных в .NET:

[source,csharp]
----
string connectionString =
                "User=SYSDBA;" +
                "Password=masterkey;" +
                "Database=G:\\Databases\\ODS12\\CRYPT.FDB;" +
                "DataSource=localhost;" +
                "Port=3053;" +
                "Dialect=3;" +
                "Charset=NONE;" +
                "Role=;" +
                "Connection lifetime=15;" +
                "Pooling=true;" +
                "MinPoolSize=0;" +
                "MaxPoolSize=50;" +
                "Packet Size=8192;" +
                "ServerType=0;" +
                "cryptkey = TXlLZXk6MHhlYywweG...;";
----

Вы можете заметить, что ключ шифрования выглядит иначе, чем в примере для нативных приложений и JayBird, это потому, что он является результатом преобразования Base64. Поэтому для получения ключа для приложений .NET необходимо вычислить Base64 из строки:

----
"MyKey:0xec,0xa1,0x52,0xf6,0x4d,0x27,0xda,0x93,0x53,0xe5,0x48,0x86,0xb9,0x7d,0xe2,0x8f,0x3b,0xfa,0xb7,0x91,0x22,0x5b,0x59,0x15,0x82,0x35,0xf5,0x30,0x1f,0x04,0xdc,0x75,"
----

и использовать его в качестве параметра для `"cryptkey=xxx;"` с точкой с запятой в конце строки подключения.

Например, в C#:

[source,csharp]
----
string plain = "MyKey:0xec,0xa1,0x52,...,0xdc,0x75,";
string cryptKey = Convert.ToBase64String(Encoding.ASCII.GetBytes(plain));
----
