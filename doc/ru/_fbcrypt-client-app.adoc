= Как работает шифрование Firebird на стороне клиента

== Нативные приложения

Чтобы понять, что происходит, когда клиентское приложение подключается к зашифрованной базе данных, рассмотрим обычный процесс подключения к незашифрованной базе данных для нативных приложений.

Обратите внимание: далее и далее под "`нативным`" подразумевается приложение, устанавливающее сетевое соединение с сервером с помощью `fbclient.dll`; обычно такие приложения создаются на Delphi, C++, PHP. В отличие от нативных приложений, Java и .NET реализуют свои собственные версии протокола, которые будут рассмотрены ниже.

Процесс подключения:

. Клиентское приложение загружает клиентскую библиотеку
.. `fbclient.dll` – нативные приложения Windows
.. `libfbclient.so` – нативные приложения Linux
. Клиентское приложение инициирует соединение, отправляя
.. Имя пользователя, например, SYSDBA
.. Пароль, например, masterkey
.. Путь/псевдоним базы данных

В случае зашифрованной базы данных требуется дополнительный шаг: необходимо передать имя ключа шифрования и его значение.

Важно отметить, что передача ключа должна выполняться до обычного соединения, поскольку страницы данных с метаданными, включая имя владельца базы данных, кодировку и т. д., зашифрованы.

Таким образом, это приводит нас к следующему:

. Необходим дополнительный сетевой обмен данными для передачи ключа до обычного соединения.

. Передача ключа из клиентского приложения в Firebird требует написания кода с использованием асимметричного шифрования и реализации интерфейса обратного вызова, что может быть довольно сложным. Для упрощения этой задачи разработчики плагинов предоставляют пример кода для подключения или, как в рамках плагинов IBSurgeon, создают дополнительную библиотеку `fbcrypt.dll`/`libfbcrypt.so`, которая реализует простой в использовании подходящий интерфейс для передачи ключей из клиентского приложения.

Библиотека `fbcrypt.dll`/`libfbcrypt.so` экспортирует три простых функции, которые следует вызывать перед тем как ваше приложение установит соединение с базой данных:

* `int __stdcall fbcrypt_init(const char* clientPathName)` - указывает путь к клиентской библиотеке;
* `int __stdcall fbcrypt_key(const char* name, const unsigned char* data, unsigned dl)` - передача имени ключа и самого ключа и его длины;
* `int __stdcall fbcrypt_callback(void* provider)` - регистрация функции обратного вызова. Если вызов этой функции происходит с использованием объектного API, то в качестве аргумента желательно передать указатель на текущий провайдер (`IProvider`), в противном случае передаём `nullptr`.

Все функции возвращают `0`, если функция выполнилась без ошибок, и значение `< 0` в противном случае.

Коды ошибок:

fbcrypt_init::
* `-1` клиентская библиотека с указанным именем не может быть загружена.
fbcrypt_key::
* `-1` неизвестная ошибка сохранения ключа, возможно нехватка памяти.
fbcrypt_callback::
* `-10` клиентская библиотека не была загружена с помощью `fbcrypt_init`;
* `-5` в библиотеке, загруженной с помощью `fbcrypt_init`, отсутствует вызов `fb_get_master_interface` - как правило очень старый (<=2.5) `fbclient` или вообще "не та" библиотека;
* `-1` неизвестная ошибка регистрации сохранённых ключей в `fbclient` - обычно не возникает.

Для подключения нативного приложения (использующего `fbclient.dll`) к зашифрованной базе данных необходимо выполнить 3 вызова. Ниже приведен пример на Delphi (упрощенный, без обработки ошибок):

В обработчике события `BeforeConnect`:

[source,pascal]
----
const keyRed: array [0..31] of byte  = ($ec,$a1,$52,$f6,$4d,$27,$da,$93,$53,$e5,$48,$86,$b9,$7d,$e2,$8f,$3b,$fa,$b7,$91,$22,$5b,$59,$15,$82,$35,$f5,$30,$1f,$04,$dc,$75);

fbcrypt_init(PAnsiChar('C:\Firebird30\fbclient.dll'));
fbcrypt_key(PAnsiChar('RED'), @keyRed, SizeOf(keyRed));
fbcrypt_callback(nil);

 // Then connect as usual
Database1.Active:=True;
----

=== А как насчет потокобезопасности в случае многопоточных клиентских приложений?

Позвольте напомнить вам несколько общих моментов реализации многопоточных клиентских приложений.

Начиная с Firebird 2.5, несколько потоков внутри приложения могут безопасно использовать одно подключение к базе данных, поскольку вся необходимая синхронизация выполняется внутри `fbclient.dll`.

Однако в этом случае потоки смогут работать с подключением только по очереди.

Это приемлемо для приложений, которые не требуют высокопроизводительного обмена данными с базой данных — если ожидание выполнения SQL-запроса одним потоком, пока другой поток выполняет другой SQL-запрос, не является проблемой, проще использовать простую модель, когда одно подключение используется несколькими потоками.

Если приложение требует параллельного выполнения SQL-запросов (т.е. это полномасштабное клиентское приложение), лучше использовать отдельное подключение к БД для каждого потока.

Ситуация с обменом ключами для подключений к зашифрованным базам данных несколько сложнее.

При каждом подключении клиентская библиотека передает ключи от клиента, но это не связано напрямую с потоками в клиентском приложении, ситуация зависит от используемого API.

Как известно, клиентская библиотека Firebird, начиная с версии 3.0, предлагает 2 типа API: новый объектно-ориентированный API, основанный на концепции провайдеров, и устаревший isc_ API, реализованный в качестве обходного пути для поддержания совместимости со старыми драйверами Firebird.

Если используется новый объектно-ориентированный клиентский API, достаточно создать провайдер, предоставить ему необходимые ключи, а затем использовать его для новых подключений.

Если используется клиентский isc_ API, для каждого подключения клиентская библиотека будет создавать свой собственный временный провайдер, который не виден и недоступен для конечного пользователя.

В этом случае ключ передается непосредственно из потока, где вызывается `isc_attach_database`, а для хранения этого ключа используется локальное хранилище потока.

*На практике, поскольку почти все клиентские библиотеки используют isc_ API (на данный момент среди популярных драйверов только драйвер Python использует объектно-ориентированный API), необходимо вызывать `fb_database_crypt_callback()` в каждом потоке, подключающемся к зашифрованной базе данных.*

Вызовы функции передачи ключа (вызовы `fbcrypt.dll` в примере https://ib-aid.com/download-demo-firebird-encryption-plugin[FEPF]) должны выполняться до установления соединения, в том же потоке, где будет установлено соединение.

При работе со множеством баз данных (например, веб-сервер SaaS с множеством клиентских баз данных) важно помнить, что каждый вызов `fbcrypt_key()` добавляет ключ в хранилище `KeyHolder`, связанный с текущим соединением.

Значения ключей должны быть установлены до установления соединения; после подключения значение ключа изменить нельзя.

В случае отсоединения ключи не выгружаются, они будут храниться в памяти до выгрузки `fbcrypt.dll`.

== Legacy приложения без исходных кодов

Что если вы хотите использовать шифрование базы данных, но для вашего приложения нет исходных кодов? Мы предусмотрели такую ситуацию. В этом случае вам необходимо создать динамическую библиотеку с именем `KeySource.dll` и положить её рядом с `fbclient.dll`. В этом случае `fbclient` ищет динамическую библиотеку с именем `KeySource.dll` и вызывает функцию `MakeKeys`, которая предоставляет необходимые ключи.

Код динамической библиотеки `KeySource.dll` тривиален.

Пример на языке C/C++:

[source,cpp]
----
#include <stdio.h>
#include <string.h>

const char* keys =
"Key=Zero 0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,0x30,\n"
"Key=White 0x25,0x83,0x46,0x88,0xf4,0x1d,0x2c,0x69,0x48,0x53,0x7a,0x4a,0x0a,0x15,0x35,0x22,0x2c,0x02,0x4f,0x65,0xb8,0x73,0x77,0x07,0x89,0xb2,0xc6,0x04,0xda,0xe4,0x03,0x5d,\n";

extern "C" char* MakeKeys(char* (*allocator)(unsigned int size), unsigned int* size)
{
	*size = strlen(keys);			// store keys length
	char* rc = allocator(*size);	// allocate memory for keys data
	memcpy(rc, keys, (*size) + 1);	// store keys data

	return rc;
}
----

Здесь функция `MakeKeys` возвращает сразу несколько именованных ключей. Ключи представляют собой нуль-терминированную строку. Каждый ключ имеет имя. Ключи отделяются переводом строки. Формат ключа следующий

[source,cmd]
----
Keys ::= "<key>\n [ <key>\n ]""

key ::= Key=<KeyName> <key_value>

<key_value> ::= 0x<hex-pair>, [0x<hex-pair>, ...]
----

У каждого ключа есть имя, которое записывается после `Key=`. Далее после отступа следует сам ключ, длинной 32-байта. Каждый байт записывается как 16-ричная пара. Каждый байт отделяется запятой. Конечная запятая обязательна.

== Java-приложения

Драйвер Java (JayBird) имеет собственную реализацию (на чистом Java) протокола Firebird. Jaybird 4 (и 3.0.4+) добавляет поддержку коллбэков шифрования базы данных Firebird 3 в реализации протокола версии 13 на чистом Java.
Из файла https://www.firebirdsql.org/file/documentation/drivers_documentation/java/4.0.2/release_notes.html#database-encryption-support[Readme Jaybird 4]:

[quote]
____
Текущая реализация проста и поддерживает только ответ со статическим значением из свойства соединения. Имейте в виду, что ответ со статическим значением для шифрования базы данных не очень безопасен, так как он может легко привести к атакам повторного воспроизведения или непреднамеренному раскрытию ключа.

В будущих версиях Jaybird (вероятно, 5) будет добавлена ​​поддержка плагинов шифрования базы данных, требующих более сложного коллбэка.
____

На практике это означает, что нам нужно установить значение для коллбэка шифрования (обычно это имя ключа и пара ключ-значение) в свойстве соединения `dbCryptConfig`.

Например:

[source,java]
----
 edConnectionString.setText("jdbc:firebirdsql://localhost/g:/Databases/ODS12/crypt.fdb?lc_ctype=utf8&dbCryptConfig=MyKey:0xec,0xa1,0x52,0xf6,0x4d,0x27,0xda,0x93,0x53,0xe5,0x48,0x86,0xb9,0x7d,0xe2,0x8f,0x3b,0xfa,0xb7,0x91,0x22,0x5b,0x59,0x15,0x82,0x35,0xf5,0x30,0x1f,0x04,0xdc,0x75,");
----

Также можно указать строку в формате base64 — из файла readme:

[quote]
____
Строки с префиксом `base64::` остальная часть строки декодируется как base64 в байты.
Символы заполнения "=" необязательны, но если они присутствуют, то должны быть допустимыми (то есть, если вы используете заполнение, вы должны использовать правильное количество символов заполнения для длины).
Если закодированное в base64 значение содержит "+", оно должно быть экранировано как %2B в URL-адресе JDBC. Для обратной совместимости с Jaybird 3 мы не можем переключиться на URL-безопасный вариант base64.
____

В реализации подключения ключей управления в IBSurgeon такой ключ связи считается более или менее небезопасным: если шифрование сетевого протокола не включено (кстати, чтобы включить его, установите в `firebird.conf` параметр `WireCrypt=Required` и не согласуйте протокольную аутентификацию), ключ легко контролируется с помощью анализатора сетевого трафика, такого как WireShark. Поэтому, чтобы разрешить передачу ключей таким способом, необходимо установить параметр `UnsafeClient=true` в файле `KeyHolder.conf` плагина управления ключами IBSurgeon.

== Приложения .NET

Провайдер Firebird.NET реализует аналогичную схему обмена ключами для зашифрованных баз данных и также требует установки параметра `UnsafeClient=true` в файле `KeyHolder.conf` в FEPF.

Пример строки подключения для зашифрованных баз данных в .NET:

[source,csharp]
----
string connectionString =
                "User=SYSDBA;" +
                "Password=masterkey;" +
                "Database=G:\\Databases\\ODS12\\CRYPT.FDB;" +
                "DataSource=localhost;" +
                "Port=3053;" +
                "Dialect=3;" +
                "Charset=NONE;" +
                "Role=;" +
                "Connection lifetime=15;" +
                "Pooling=true;" +
                "MinPoolSize=0;" +
                "MaxPoolSize=50;" +
                "Packet Size=8192;" +
                "ServerType=0;" +
                "cryptkey = TXlLZXk6MHhlYywweG...;";
----

Вы можете заметить, что ключ шифрования выглядит иначе, чем в примере для нативных приложений и JayBird, это потому, что он является результатом преобразования Base64. Поэтому для получения ключа для приложений .NET или Java необходимо вычислить Base64 из строки:

----
"MyKey:0xec,0xa1,0x52,0xf6,0x4d,0x27,0xda,0x93,0x53,0xe5,0x48,0x86,0xb9,0x7d,0xe2,0x8f,0x3b,0xfa,0xb7,0x91,0x22,0x5b,0x59,0x15,0x82,0x35,0xf5,0x30,0x1f,0x04,0xdc,0x75,"
----

и использовать его в качестве параметра для `"cryptkey=xxx;"` с точкой с запятой в конце строки подключения.
