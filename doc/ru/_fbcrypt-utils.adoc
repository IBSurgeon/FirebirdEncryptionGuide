[[fbcrypt-utils]]
= Поддержка в консольных утилитах Firebird

Как было описано выше, главная проблема при работе с зашифрованными базами данных заключается в том, как хранить ключи шифрования. В идеальном случае ключ шифрования должен быть известен только клиентскому приложению, чтобы его невозможно было украсть. Особенно актуальна эта проблема для приложений, использующих embedded соединения, когда база данных и клиентское приложение расположены на одной и той же машине. Но как в этом случае работать с консольными утилитами Firebird, которым необходимо соединение с БД, такими как `gbak`, `nbackup` и др.?

Для того, чтобы использовать встроенные утилиты Firebird и не хранить ключ на сервере, мы модифицировали утилиты `gbak`, `nbackup`, `isql` и `gfix`. Модифицированные утилиты позволяют указывать альтернативный плагин для хранения ключа (`KeyHolder`). Также был разработан плагин `KeyHolderStdin`, который позволяет считывать ключ шифрования из входного потока консоли.

Модифицированные утилиты входят в клиентский пакет плагина шифрования (`Client\32bit`, `Client\64bit`) и в HQbird.

[[fbcrypt-utils-versions]]
== Различия между версиями Firebird

Набор переключателей зависит от версии Firebird и от того, чья это утилита: стандартная ("ванильная") или из пакета плагина.

.Какие переключатели есть в утилитах
[cols="2,2,3,3", options="header"]
|===
| Утилита | Версия | Стандартный Firebird | Пакет плагина и HQbird
| `gbak` | 3.0 | нет | `-KEYFILE`, `-KEYNAME`, `-KEY`
| `gbak` | 4.0, 5.0 | `-KEYHOLDER`, `-KEYNAME`, `-CRYPT` | `-KEYHOLDER`, `-KEYNAME`, `-CRYPT`
| `gfix`, `isql`, `nbackup` | 3.0 | нет | нет (ключ через `firebird.conf`, см. <<fbcrypt-utils-fb3>>)
| `gfix`, `isql`, `nbackup` | 4.0, 5.0 | нет | `-KEYHOLDER`
| `gstat` | 3.0, 4.0, 5.0 | `-e` | `-e`
|===

Главные выводы из таблицы:

* В Firebird 4.0 и 5.0 зашифрованную резервную копию можно сделать и стандартным `gbak`.
* Для `gfix`, `isql` и `nbackup` переключатель `-KEYHOLDER` есть только в утилитах из пакета плагина и HQbird, начиная с версии 4.0.
* В Firebird 3.0 у утилит другие переключатели. Команды из разделов для 4.0 и 5.0 в версии 3.0 не работают.

Между версиями 4.0 и 5.0 различий в переключателях нет.

== Firebird 4.0 и 5.0

=== Переключатели

[cols="1,2,4", options="header"]
|===
| Утилита | Переключатель | Назначение
| `gbak` | `-KEYHOLDER <плагин>` | Плагин управления ключами на стороне утилиты. Включает шифрование файла резервной копии.
| `gbak` | `-KEYNAME <имя>` | Имя ключа для шифрования резервной копии или восстановленной базы данных.
| `gbak` | `-CRYPT <плагин>` | Имя плагина шифрования.
| `gfix` | `-KEYHOLDER <плагин>` | Плагин управления ключами на стороне утилиты.
| `isql` | `-KEYHOLDER <плагин>` | Плагин управления ключами на стороне утилиты.
| `nbackup` | `-KEYHOLDER <плагин>` | Плагин управления ключами на стороне утилиты.
| `gstat` | `-e` | Статистика шифрования страниц (см. <<fbcrypt-monitoring>>).
|===

Регистр букв в переключателях не учитывается. Сокращения: `-KEYH`, `-KEYN`, `-CRY`.

Переключатель `-KEYHOLDER` задаёт для утилиты параметр `KeyHolderPlugin`. Утилита загружает указанный плагин из своего каталога `plugins` и через него передаёт ключ серверу по защищённому протоколу.

[IMPORTANT]
====
Рядом с утилитой должны находиться каталог `plugins` с плагинами `KeyHolderStdin`, `KeyHolder` и `DbCrypt`, файл лицензии `DbCrypt.conf` и библиотека OpenSSL.

Плагин `DbCrypt` и лицензия нужны утилите `gbak`: она сама шифрует и расшифровывает файл резервной копии. Без них `gbak` завершается ошибкой `Crypt plugin DbCrypt failed to load`.

В клиентском пакете для Windows файл `keyholderstdin.dll` лежит в каталоге `key-plugins`. Скопируйте его в каталог `plugins`. Иначе утилита сообщает `Key holder plugin KeyHolderStdin failed to load`. В HQbird этот файл уже лежит в каталоге `plugins`: копировать его не нужно.
====

[[fbcrypt-utils-stdin]]
=== Плагин KeyHolderStdin

Плагин `KeyHolderStdin` читает ключ из стандартного входного потока утилиты.

Рассмотрим пример работы `gbak` с плагином `KeyHolderStdin`:

[source,cmd]
----
echo Key=Green 0xab,0xd7,0x34,0x63,0xae,0x19,0x52,0x00,0xb8,0x84,0xa3,0x44,0xbd,0x11,0x9f,0x72,0xe0,0x04,0x68,0x4f,0xc4,0x89,0x3b,0x20,0x8d,0x2a,0xa7,0x07,0x32,0x3b,0x5e,0x74, | gbak -b localhost:"C:\Firebird\crypt-plugin\CryptClient\db-crypt\emp-crypted.fdb" "C:\Firebird\crypt-plugin\CryptClient\db-crypt\emp-crypted.fbk" -KeyHolder KeyHolderStdin
----

Здесь ключ передаётся из входного потока. Формат передачи ключа следующий:

[source,cmd]
----
Key=<KeyName> <key_value>

<key_value> ::= 0x<hex-pair>,[0x<hex-pair>,...]
----

Здесь `<KeyName>` - имя ключа, которое должно совпадать с именем ключа, используемым при шифровании базы данных.

Вместо ключа можно передать парольную фразу (см. <<fbcrypt-keygen-password>>):

[source,cmd]
----
Password=<KeyName> <passphrase>
----

Процесс генерации ключей описан в <<fbcrypt-keygen>>.

Особенности плагина:

* Плагин принимает *один* ключ. Весь входной поток читается как одна строка `Key=` или `Password=`.
* Если входной поток пуст, утилита завершается с ошибкой `No input`.
* Входной поток занят ключом. Поэтому команды для `isql` передавайте в файле с помощью переключателя `-i`, а не через входной поток.

==== Ключ из файла

Команда `echo` с ключом остаётся в истории команд и видна в списке процессов. Надёжнее хранить строку с ключом в файле с ограниченным доступом.

Windows:

[source,cmd]
----
type C:\Secure\dbkey.txt | gbak -b localhost:D:\DB\app.fdb E:\Backup\app.fbk -KeyHolder KeyHolderStdin -user SYSDBA -password ********
----

Linux:

[source,bash]
----
gbak -b localhost:/data/app.fdb /backup/app.fbk -KeyHolder KeyHolderStdin -user SYSDBA -password '********' < /secure/dbkey.txt
----

Файл `dbkey.txt` содержит одну строку:

[source]
----
Key=MyKey 0x35,0xa1,...,0x1e,
----

Рекомендации для запуска по расписанию:

* Запускайте задание от отдельной служебной учётной записи.
* Дайте права на чтение файла с ключом только этой учётной записи.
* Регулярно проверяйте восстановление из резервной копии на тестовом сервере.

==== Ключ из программы

Приложение может запустить утилиту как дочерний процесс и записать ключ в её входной поток. Тогда ключ не хранится в файле. Пример на C для Linux:

[source,c]
----
#include <stdio.h>

int main()
{
	FILE* f = popen("./gbak -b -KeyHolder KeyHolderStdin /mnt/db/stdin.fdb std.fbk", "w");
	const char* key = "Key=Red 0xec,0xa1,0x52,0xf6,0x4d,0x27,0xda,0x93,0x53,0xe5,0x48,0x86,0xb9,"
					  "0x7d,0xe2,0x8f,0x3b,0xfa,0xb7,0x91,0x22,0x5b,0x59,0x15,0x82,0x35,0xf5,0x30,0x1f,0x04,0xdc,0x75,";

	if (f)
	{
		fputs(key, f);
		int x = pclose(f);
		if (x)
			printf("gbak error, code %d\n", x >> 8);
	}
	else
		perror("popen gbak");
}
----

[[fbcrypt-utils-gbak]]
=== Резервное копирование и восстановление (gbak)

[WARNING]
====
Утилита `gbak` шифрует файл резервной копии только тогда, когда указан переключатель `-KEYHOLDER`.

Если `gbak -b` запущен без этого переключателя и смог подключиться к базе данных (ключ есть на сервере в файле `KeyHolder.conf` или его передала библиотека `KeySource` клиента), файл `.fbk` будет *не зашифрован*. Данные в нём лежат в открытом виде.
====

При резервном копировании с переключателем `-KEYHOLDER` утилита берёт имя ключа и имя плагина шифрования из базы данных. Переключатели `-KEYNAME` и `-CRYPT` нужны, только если вы хотите указать другие значения.

.Зашифрованная резервная копия
[source,cmd]
----
echo Key=Green 0xab,0xd7,...,0x74, | gbak -b localhost:C:\db\emp-crypted.fdb C:\db\emp-crypted.fbk -KeyHolder KeyHolderStdin -user SYSDBA -password masterkey
----

.Восстановление в зашифрованную базу данных
[source,cmd]
----
echo Key=Green 0xab,0xd7,...,0x74, | gbak -c C:\db\emp-crypted.fbk localhost:C:\db\emp-restore.fdb -KeyHolder KeyHolderStdin -user SYSDBA -password masterkey
----

При восстановлении `gbak` читает имя ключа и плагина из заголовка файла резервной копии. Новая база данных шифруется сразу после создания. Чтобы зашифровать её другим ключом, укажите `-KEYNAME <новое имя>` (ключ с этим именем должен быть доступен утилите и серверу).

Если ключи находятся на сервере в файле `KeyHolder.conf`, вместо `KeyHolderStdin` можно использовать плагин `KeyHolder`. В этом случае `gbak` запускается на сервере и читает тот же файл. Так работает и стандартный `gbak` Firebird 4.0 и 5.0:

[source,bash]
----
gbak -b -user SYSDBA -password masterkey -keyholder KeyHolder -keyname Red -crypt DbCrypt localhost:employee /backup/employee.fbk
----

==== Ключ из библиотеки KeySource

Плагин `KeyHolder` в каталоге утилиты берёт ключ у библиотеки `KeySource`, которая лежит рядом с `fbclient` (см. <<fbcrypt-keysource>>). Ключа нет ни в команде, ни во входном потоке:

[source,cmd]
----
gbak -b -KeyHolder KeyHolder -user SYSDBA -password masterkey localhost:C:\db\emp-crypted.fdb C:\db\emp-crypted.fbk
gbak -c -KeyHolder KeyHolder -user SYSDBA -password masterkey C:\db\emp-crypted.fbk localhost:C:\db\emp-restore.fdb
----

Результат `gbak -b` зависит от команды и от файлов в каталоге `plugins` утилиты:

[cols="3,3,3", options="header"]
|===
| В каталоге `plugins` утилиты | Команда | Результат
| только `keyholder.dll` | `gbak -b` | копия *не зашифрована*
| только `keyholder.dll` | `gbak -b -KeyHolder KeyHolder` | ошибка `Crypt plugin DbCrypt failed to load`
| `keyholder.dll`, `dbcrypt.dll`, `DbCrypt.conf` | `gbak -b` | копия *не зашифрована*
| `keyholder.dll`, `dbcrypt.dll`, `DbCrypt.conf` | `gbak -b -KeyHolder KeyHolder` | копия зашифрована
|===

Восстановление зашифрованной копии без ключа завершается ошибкой `Unknown key name <имя> - key can't be found`.

Готовый пример с пробным восстановлением: скрипт `examples/closed-gui/deploy/50-backup.ps1` в репозитории https://github.com/IBSurgeon/FirebirdEncryptionGuide.

==== Как убедиться, что копия зашифрована

* В незашифрованной копии имена таблиц записаны обычным текстом. Команда `findstr /m CUSTOMER emp-crypted.fbk` (Linux: `grep -l CUSTOMER emp-crypted.fbk`) выводит имя файла, если нашла в нём слово. Для зашифрованной копии она не выводит ничего. Подставьте имя таблицы своей базы данных.
* Восстановление без ключа должно завершиться ошибкой.
* Регулярно восстанавливайте копию на тестовом сервере.

[NOTE]
====
Для восстановления в новый файл параметр `KeyHolderPlugin` должен быть задан в `firebird.conf`. Настройка в `databases.conf` действует только для своего псевдонима и на новый файл не распространяется.
====

=== nbackup

Утилита `nbackup` копирует страницы базы данных как есть. Копия остаётся зашифрованной тем же ключом, что и база данных. Ключ нужен утилите для подключения к базе данных:

[source,cmd]
----
echo Key=Green 0xab,0xd7,...,0x74, | nbackup -b 0 localhost:C:\db\emp-crypted.fdb C:\db\emp-nbackup.fdb -KeyHolder KeyHolderStdin -user SYSDBA -password masterkey
----

Команда `gstat -h` для файла копии показывает атрибут `encrypted` и то же имя ключа, что у базы данных. Если ключ даёт библиотека `KeySource`, укажите `-KeyHolder KeyHolder` и не передавайте ничего во входной поток.

=== gfix

[source,cmd]
----
echo Key=Green 0xab,0xd7,...,0x74, | gfix -v -full -KeyHolder KeyHolderStdin localhost:C:\db\emp-crypted.fdb -user SYSDBA -password masterkey
----

=== isql

[source,cmd]
----
echo Key=Green 0xab,0xd7,...,0x74, | isql -KeyHolder KeyHolderStdin -user SYSDBA -password masterkey -i script.sql localhost:C:\db\emp-crypted.fdb
----

Так можно зашифровать базу данных, не записывая ключ в файл на сервере. Файл `script.sql`:

[source,sql]
----
alter database encrypt with "DbCrypt" key Green;
commit;
show database;
----

Тот же оператор можно выполнить из каталога клиента, в котором лежит библиотека `KeySource` и в файле `firebird.conf` есть строка `KeyHolderPlugin = KeyHolder`. Тогда не нужны ни переключатель, ни входной поток. Этот способ работает и в версии 3.0.

[[fbcrypt-utils-fb3]]
== Firebird 3.0

Стандартные утилиты Firebird 3.0 не имеют переключателей для ключей. Используйте утилиты из клиентского пакета плагина шифрования для Firebird 3.0 или из HQbird 3.

=== gbak

[cols="2,4", options="header"]
|===
| Переключатель | Назначение
| `-KEYFILE <файл>` | Файл с ключами. Формат строк такой же, как в `KeyHolder.conf`: `Key=<имя> <значение>`. Можно указать сам файл `KeyHolder.conf`.
| `-KEY <значение>` | Значение ключа в записи `0x..,0x..,`. Требует `-KEYNAME`. Нельзя использовать вместе с `-KEYFILE`.
| `-KEYNAME <имя>` | Имя ключа. Требует `-KEYFILE` или `-KEY`. Если имя не указано, при резервном копировании оно берётся из базы данных.
|===

Сокращения: `-KEYF`, `-KEYN`. Переключателей `-KEYHOLDER` и `-CRYPT` в версии 3.0 нет. Имя плагина шифрования всегда `DbCrypt`.

Если указан `-KEYFILE` или `-KEY`, утилита передаёт ключ серверу для подключения и шифрует файл резервной копии.

.Зашифрованная резервная копия, ключ из файла
[source,bash]
----
gbak -b -user SYSDBA -password masterkey -keyfile /opt/firebird/plugins/KeyHolder.conf -keyname Red localhost:employee /backup/employee.fbk
----

.Зашифрованная резервная копия, ключ в командной строке
[source,cmd]
----
gbak -b -user SYSDBA -password masterkey -key 0xec,0xa1,...,0x75, -keyname Red localhost:C:\db\emp-crypted.fdb C:\db\emp-crypted.fbk
----

.Восстановление в зашифрованную базу данных
[source,bash]
----
gbak -c -user SYSDBA -password masterkey -keyfile /opt/firebird/plugins/KeyHolder.conf -keyname Red /backup/employee.fbk localhost:/data/employee_restored.fdb
----

[WARNING]
====
Ключ в переключателе `-KEY` виден в списке процессов и остаётся в истории команд. Предпочитайте `-KEYFILE` с файлом, доступ к которому ограничен.

Если `gbak -b` запущен без `-KEYFILE` и `-KEY`, а ключ есть на сервере, файл `.fbk` будет *не зашифрован*.
====

На Linux утилита `gbak` из клиентского пакета 3.0 загружает OpenSSL по имени `libcrypto.so`, без номера версии. Ей нужна ссылка `libcrypto.so` на OpenSSL 1.1 в её каталоге `lib`. Без ссылки `gbak` завершается ошибкой `Error loading OpenSSL dynamic library libcrypto.so`. Шифрование базы и `nbackup` работают и без ссылки. В Debian и Ubuntu библиотека находится в `/usr/lib/x86_64-linux-gnu`, а не в `/usr/lib64`.

[source,bash]
----
cp -r /root/crypt/Client /opt/fbcrypt-client
ln -sf /usr/lib64/libcrypto.so.1.1 /opt/fbcrypt-client/lib/libcrypto.so
----

=== gfix, isql, nbackup и плагин KeyHolderStdin

В версии 3.0 у этих утилит нет переключателя `-KEYHOLDER`. Плагин управления ключами для них задаётся в файле `firebird.conf`, который лежит в каталоге утилиты (каталог клиентского пакета):

[source,conf]
----
KeyHolderPlugin = KeyHolderStdin
----

После этого ключ передаётся через входной поток, как в версиях 4.0 и 5.0, но без переключателя:

[source,cmd]
----
echo Key=Green 0xab,0xd7,...,0x74, | gfix -v -full localhost:C:\db\emp-crypted.fdb -user SYSDBA -password masterkey
----

Так же можно указать `KeyHolderPlugin = KeyHolder`. Тогда утилита берёт ключи из файла `plugins/KeyHolder.conf` или из библиотеки `KeySource` в своём каталоге.

Утилита `gbak` 3.0 без `-KEYFILE` и `-KEY` тоже использует плагин из `firebird.conf`. Если плагин передал ключ, файл резервной копии шифруется. С плагином `KeyHolder` ключ даёт библиотека `KeySource`, с плагином `KeyHolderStdin` входной поток.

Для этого в каталоге `plugins` утилиты нужны `dbcrypt.dll` и лицензия `DbCrypt.conf`. Без них `gbak` 3.0 не создаёт файл и завершается ошибкой `Crypt plugin DbCrypt failed to load`.

В клиентском пакете для Windows файл `keyholderstdin.dll` лежит в каталоге `key-plugins`. Скопируйте его в каталог `plugins`. Иначе утилита версии 3.0 сообщает `Key not set`.

[NOTE]
====
Параметр `KeyHolderPlugin` в `firebird.conf` действует на все программы, которые используют клиентскую библиотеку из этого каталога. С плагином `KeyHolderStdin` каждая из них будет читать входной поток при подключении. Держите утилиты для обслуживания в отдельном каталоге.
====

== Утилита decrypt

В серверном пакете для Windows есть утилита `decrypt`. Она расшифровывает файл базы данных напрямую, без сервера Firebird:

[source,cmd]
----
decrypt <файл базы данных>
----

Утилита читает имя ключа из заголовка базы данных и берёт ключ из файла `plugins/KeyHolder.conf`. Перед запуском:

. Остановите все подключения к базе данных.
. Сделайте копию файла базы данных. Утилита изменяет файл на месте.
. Запишите ключ в `KeyHolder.conf`.

Обычный способ расшифровки -- оператор `ALTER DATABASE DECRYPT` (см. <<fbcrypt-usage>>). Утилита `decrypt` нужна в особых случаях, например для работы с повреждённой базой данных.
