[[fbcrypt-usage]]
= Шифрование, расшифровка и смена ключа

В этой главе описаны основные операции с зашифрованной базой данных.

== Перед началом

Проверьте следующее:

. Сделана резервная копия базы данных. Первые опыты выполняйте только на копии.
. Плагин установлен, файл лицензии `DbCrypt.conf` находится в каталоге `plugins` (см. <<fbcrypt-install>>).
. В `firebird.conf` или в `databases.conf` задан параметр `KeyHolderPlugin = KeyHolder`.
. Ключ создан, и его копия сохранена вне сервера (см. <<fbcrypt-keygen>>).
. Серверу доступен ключ. Есть три способа:
** временно записать ключ в файл `plugins/KeyHolder.conf`;
** передать ключ из клиента утилитой `isql` с плагином `KeyHolderStdin` (см. <<fbcrypt-utils>>);
** выполнить оператор утилитой `isql` из каталога клиента, в котором лежит библиотека `KeySource` (см. <<fbcrypt-keysource>>). Ключ серверу передаёт клиентский плагин `KeyHolder`, файл на сервере не нужен.

Если ключ передаёт клиент, подключайтесь по TCP/IP (`localhost:` или `inet://`), а не по локальному пути без имени сервера и не по XNET. См. <<fbcrypt-connection-kinds>>.

[[fbcrypt-connection-kinds]]
== Виды подключений

Сервер Firebird запрашивает ключ у клиента только при подключении по TCP/IP. При подключении по XNET ключ должен быть на сервере.

[cols="3,2,2", options="header"]
|===
| Подключение | Ключ в файле `KeyHolder.conf` на сервере | Ключ передаёт клиент
| TCP/IP: `сервер:база`, `сервер/порт:база`, `inet://сервер:порт/база`
| работает
| работает

| XNET: `xnet://база`. Только Windows, клиент и сервер на одном компьютере
| работает
| не работает, ошибка `Key not set`
|===

Ключ передаёт клиент в каждом из этих способов: `fbcrypt`, `KeySource`, `KeyHolderStdin`, ключ `-KeyHolder` утилит. Правило задаёт сервер Firebird, поэтому оно одно для всех способов.

* *Локальный путь без имени сервера (Windows).* Результат зависит от параметра `Providers` клиента. Провайдер `Engine13` (в 3.0: `Engine12`) открывает файл внутри процесса клиента: это режим embedded, сети нет, ключ получает плагин `KeyHolder` этого процесса. Провайдер `Loopback` в Windows сначала пробует XNET, и ключ клиента не передаётся. Если в `Providers` есть только `Remote`, подключение завершается ошибкой `unavailable database`. Пишите имя сервера, и результат не будет зависеть от настроек.
* *Шифрование канала.* По XNET данные идут через общую память компьютера. Плагины `WireCrypt` их не шифруют: `WIRE_ENCRYPTED = FALSE`. Это штатное поведение Firebird.
* *WNET (именованные каналы).* Есть только в Firebird 3.0 и 4.0. Не проверен. По исходному коду сервера правило то же, что для XNET.
* *Имя XNET.* Если на сервере задан параметр `IpcName`, то же значение нужно в `firebird.conf` клиента.

Проверено 24.11.2026 на Firebird 3.0.14, 4.0.7 и 5.0.4 для Windows: `isql` с библиотекой `KeySource` и `gbak` (на 4.0 и 5.0 с ключом `-KeyHolder KeyHolder`).

== Шифрование базы данных

[source,sql]
----
ALTER DATABASE ENCRYPT WITH "DbCrypt" KEY Red;
COMMIT;
----

[cols="1,3", options="header"]
|===
| Элемент | Замечание
| `"DbCrypt"`
| Имя плагина шифрования. На Linux имя зависит от регистра, поэтому пишите его в двойных кавычках. На Windows кавычки не обязательны.

| `Red`
| Имя ключа. Без кавычек имя сохраняется в верхнем регистре (`RED`). Плагин `KeyHolder` сравнивает имена без учёта регистра.
|===

Оператор только запускает шифрование. Страницы шифрует фоновый поток сервера:

* Шифрование идёт, пока к базе данных есть хотя бы одно подключение. Для большой базы данных держите подключение открытым до конца шифрования.
* С базой данных можно работать во время шифрования.
* Если сервер был остановлен, шифрование продолжится при следующем подключении с ключом.

Как проверить, что шифрование завершено, описано в <<fbcrypt-monitoring>>.

[WARNING]
====
После шифрования выполните `gstat -h`: в строке `Attributes` должно быть слово `encrypted`.

Оператор `ALTER DATABASE ENCRYPT` может завершиться без ошибки и не зашифровать базу данных. Так происходит на Firebird 3.0, 4.0 и 5.0, когда ключ задан в файле `KeyHolder.conf` парольной фразой с фигурными скобками. Допустимые символы фразы перечислены в <<fbcrypt-keygen-password>>.
====

После завершения шифрования:

. Если ключ был записан в `plugins/KeyHolder.conf` только для шифрования, удалите или переименуйте этот файл и перезапустите Firebird. Без файла `KeyHolder.conf` сервер работает: он нужен только для параметров плагина (см. <<fbcrypt-config-keyholder>>).
. Проверьте, что без ключа подключиться нельзя.
. Проверьте работу приложений и резервного копирования.

== Расшифровка базы данных

[source,sql]
----
ALTER DATABASE DECRYPT;
COMMIT;
----

Расшифровка тоже выполняется в фоновом потоке. Не удаляйте ключ и параметр `KeyHolderPlugin`, пока `gstat -h` показывает атрибут `encrypted`.

== Смена ключа

Firebird не умеет заменить ключ зашифрованной базы данных одной командой. Попытка выполнить `ALTER DATABASE ENCRYPT` для уже зашифрованной базы данных завершается ошибкой. Есть два способа сменить ключ.

*Способ 1. Расшифровать и зашифровать заново.*

. Выполните `ALTER DATABASE DECRYPT` и дождитесь завершения.
. Выполните `ALTER DATABASE ENCRYPT WITH "DbCrypt" KEY <новое имя>`.

Между шагами база данных лежит на диске в открытом виде. Обе операции читают и записывают все страницы.

*Способ 2. Резервная копия и восстановление.*

. Сделайте резервную копию утилитой `gbak`.
. Восстановите её в новую базу данных с параметром `-KEYNAME <новое имя>`.

См. <<fbcrypt-utils-gbak>>.

[TIP]
====
Давайте новому ключу новое имя. По имени ключа в заголовке (`gstat -h`) всегда видно, каким ключом зашифрована база данных или её копия.
====

== Кто может шифровать базу данных

Операторы `ALTER DATABASE ENCRYPT` и `ALTER DATABASE DECRYPT` может выполнить владелец базы данных, администратор (`SYSDBA`, роль `RDB$ADMIN`) или пользователь с привилегией `ALTER DATABASE`.

Шифрование не заменяет разграничение прав. Пользователь, который подключился с правильным ключом, видит данные согласно своим правам SQL.
