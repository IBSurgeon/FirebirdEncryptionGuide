= Как работает шифрование базы данных Firebird на стороне сервера

Давайте рассмотрим внутренние детали шифрования базы данных Firebird, начнем с серверной части.

== Какая часть базы данных подвергается шифрованию?

Первое, что нам нужно рассмотреть, это какая часть базы данных шифруется? Как вы, вероятно, знаете, база данных Firebird состоит из частей одинакового размера, называемых "`страницами базы данных`". Существует несколько типов таких страниц, каждый тип служит определенной цели.

Ниже вы можете увидеть рисунок с основными типами данных:

.Типы страниц базы данных
image::1_firebird_database_data_pages.png[]

Некоторые страницы предназначены для хранения данных пользователей, а другие необходимы для хранения системной информации, например, страницы транзакций и инвентаризации страниц (более подробная информация о страницах базы данных https://ib-aid.com/en/articles/database-physical-structure-interbase-and-firebird/[доступна здесь]).

При шифровании базы данных Firebird шифруются только страницы с пользовательскими данными: страницы данных, индексов, генераторов и BLOB-объектов.

.Шифрование применяется только к страницам базы данных, содержащим данные пользователей
image::2_firebird_encrypted_pages.png[]

Обратите внимание, что метаданные базы данных (хранимые процедуры, таблицы, представления, имена триггеров, генераторов и т. д.) не отличаются от "`данных пользователей`" в той части механизма, которая отвечает за шифрование, и они шифруются.

Почему системные страницы не шифруются? В основном, по соображениям производительности и потому, что они не содержат конфиденциальных данных, требующих защиты.

Заголовочная страница базы данных не шифруется, поскольку содержит информацию, необходимую для шифрования (например, имя ключа).

== Когда происходит шифрование страниц данных?

Когда пользователь выполняет запрос SELECT к зашифрованной базе данных, данные считываются из зашифрованного файла, но поступают в приложение с результирующим набором в незашифрованном виде.

Рассмотрим подробности этого процесса:

.Когда происходит шифрование страниц базы данных?
image::3_when_pages_encrypted.png[]

Обычно процесс начинается с серии чтений страниц базы данных из файла базы данных, которые кэшируются в файловом кэше операционной системы.

Firebird также можно настроить на обход файлового кэша и использование только собственного кэша, но по умолчанию используется файловый кэш.

После этого Firebird считывает страницы и помещает их в кэш страниц Firebird (его размер определяется параметром `DefaultDBCachePages` в `firebird.conf` и/или `databases.conf` или в заголовочной странице базы данных).

Затем страницы из кэша выбираются в результирующий набор конкретного SQL-запроса (`SELECT` в нашем примере).

Подробности показаны на рисунке ниже:

Таким образом, страницы базы данных зашифрованы в файловом кэше операционной системы, но поступают в кэш страниц Firebird в незашифрованном виде, и наоборот.

Часть программного обеспечения Firebird, отвечающая за шифрование/дешифрование, называется "`плагином шифрования`". Поскольку большинство реализаций плагинов (известных авторам) называются `DbCrypt`, мы будем называть его `DbCrypt`.

На рисунке ниже вы можете увидеть варианты для Windows (`DbCrypt.dll`) и Linux (`libDbCrypt.so`):

.Плагин шифрования (DbCrypt) выполняет шифрование/дешифрование
image::6_firebird_dbcrypt.png[]

Если вы достаточно долго будете смотреть на эту картинку, довольно быстро возникнет следующий вопрос: как `DbCrypt` получает правильный ключ для шифрования/расшифровки страниц базы данных?

Ответ -- существует другой плагин для управления ключами.

Обычно для управления ключами используется плагин под названием `KeyHolder`, который служит средством хранения/управления ключами для плагина шифрования (`DbCrypt`). `KeyHolder` реализует интерфейс управления ключами, используемый `DbCrypt`.

[NOTE]
====
Также (в случае соответствующего написания кода плагина шифрования) он способен самостоятельно загружать ключ, например с внешнего flash USB, но в данном документе этот вариант не рассматривается.
====

*Что означает "`управление ключами`"?*

В простейшем случае `DbCrypt` может считывать ключи из файла на сервере. Файл может быть простым текстовым файлом, который может быть спрятан в "`секретном`" месте или на USB-накопителе, или может быть зашифрованным файлом (например, с использованием Windows Crypto API или со встроенным внутренним ключом).

Файл ключей может содержать несколько ключей, хранящихся для удобства в виде именованного списка, и может выглядеть следующим образом (пример ниже взят из фреймворка плагинов шифрования IBSurgeon):

[listing]
----

Key=Green 0xab,0xd7,0x34,0x63,0xae,0x19,0x52,0x00,0xb8,0x84,0xa3,0x44,0xbd,0x11,0x9f,0x72,0xe0,0x04,0x68,0x4f,0xc4,0x89,0x3b,0x20,0x8d,0x2a,0xa7,0x07,0x32,0x3b,0x5e,0x74,

Когда база данных зашифрована, её заголовок (нулевая страница) остаются незашифрованной и хранят в том числе информацию о плагине шифрования и имени ключа. Заголовок защищён зашифрованными хешами, предотвращающими попытки расшифровать БД с помощью изменения его состояния. Эту информацию можно просмотреть с помощью команды `gstat -h databasename`:

=== Выбор правильного ключа

Часто разработчики задают вопрос: "`Как плагин определяет, какой ключ для какой базы данных?`" Ответ довольно прост: по имени ключа, которое хранится на странице заголовка базы данных.

Реже, но всё же важный вопрос: что если имя ключа совпадает с именем, указанным в заголовке, но значение ключа отличается? Чтобы предотвратить ошибки чтения страницы из-за неправильного ключа, плагин `DbCrypt` сохраняет зашифрованную тестовую последовательность (цифры 0...F) в заголовке, затем активирует ключ, пытается зашифровать тестовые данные с помощью ключа и сравнивает его хеш с сохраненным результатом, чтобы убедиться, что переданное значение ключа действительно корректно для данной конкретной базы данных.

Подход, при котором плагин шифрования считывает ключи напрямую, прост и удобен для отладки, тестирования производительности и т. д., поскольку он реализует шифрование прозрачным образом: то есть клиентские приложения и инструменты разработчиков не знают, что база данных зашифрована.

Однако в реальности необходимо ограничить доступ приложений к базе данных: только клиентское приложение, имеющее ключ, должно иметь возможность подключаться к зашифрованной базе данных.

Для этого нам нужен плагин `KeyHolder`, позволяющий получить ключ из клиентского приложения (которое обычно находится на другом компьютере) по сетевому протоколу Firebird.

== Как защитить передачу ключей?

Возможно, нам потребуется защитить базу данных в ситуации, когда клиент решает получить прямой доступ к зашифрованной базе данных, минуя авторизованные приложения (многие поставщики хотят ограничить доступ к данным, разрешив только доступ из специального приложения).

Это эквивалентно ситуации, когда злоумышленник имеет доступ к серверу, но не имеет ключей.

Рассмотрим следующие сценарии атаки для перехвата ключей на стороне сервера:

. Когда злоумышленник создает поддельный плагин шифрования (`DBCrypt.dll`) и размещает его на сервере, и когда `KeyHolder` передает ключ, поддельный `DbCrypt` делает дамп ключа:
+

image::11_attack_with_fake_dbcrypt.png[]

. Когда злоумышленник создает поддельный файл `firebird.exe` и делает с его помощью дамп:
+
.Атака с помощью поддельного firebird.exe
image::12_attack_with_fake_firebird.png[]

Для защиты от подобных атак, качественная реализация плагинов шифрования и управления ключами должна обеспечивать защиту обмена ключами.

Обмен ключами можно защитить с помощью асимметричного шифрования с использованием пары открытого/закрытого ключей.

Эти ключи генерируются в процессе сборки и встраиваются для конкретной пары плагинов шифрования и управления ключами. Для наилучшей защиты необходимо использовать специально созданные пары `DbCrypt`/`KeyHolder`.

image::13_key_exchange.png[]

При обмене ключами между `DbCrypt` и `KeyHolder` используется следующий протокол (он упрощен, но, думаю, суть понятна):

[listing]
----
DbCrypt → KeyHolder:
	Give Me The Database Key With this Salt
KeyHolder:
	Encrypts DbKey With Public key using salt from DbCrypt
	Transfers Encrypted DbKey to DbCrypt
DbCrypt:
	Decrypt DbKey With Private Key
	Validate salt correctness
	Ready To Work
----

Для обмена ключами между экземплярами `KeyHolder` и для обмена ключами между клиентским приложением и `KeyHolder` используется примерно один и тот же протокол.

Реализация защиты обмена ключами в плагине IbSurgeon обеспечивает также защиту данных при передаче по недружественной глобальной сети, в том числе в тех случаях когда ключ должен быть передан по каналу, ещё не готовому шифровать все данные штатным для Firebird образом. Такая ситуация возникает при использовании self security database.

[IMPORTANT]
====
Обратите внимание, что шифрование и корректность передаваемых ключей зависят от реализации плагина; движок Firebird предоставляет только базовую низкоуровневую услугу передачи: "`отправить N байтов из этого экземпляра плагина в экземпляр парного плагина`".
====

[discrete]
== Краткое описание серверной части шифрования

* Шифрование/дешифрование выполняется плагином шифрования базы данных (`DbCrypt`) постранично, во время обмена данными между файловым кэшем операционной системы и кэшем страниц Firebird.

* Управление ключами можно реализовать простым способом, когда `DbCrypt` считывает ключи напрямую, но обычно это делается с помощью плагина управления ключами (`KeyHolder`).
