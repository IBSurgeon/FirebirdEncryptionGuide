[[fbcrypt-server]]
= Как работает шифрование базы данных Firebird на стороне сервера

Давайте рассмотрим внутренние детали шифрования базы данных Firebird, начнем с серверной части.

== Какая часть базы данных подвергается шифрованию?

Первое, что нам нужно рассмотреть, это какая часть базы данных шифруется? Как вы, вероятно, знаете, база данных Firebird состоит из частей одинакового размера, называемых "`страницами базы данных`". Существует несколько типов таких страниц, каждый тип служит определенной цели.

Ниже вы можете увидеть рисунок с основными типами страниц:

.Типы страниц базы данных
image::1_firebird_database_data_pages.png[]

Некоторые страницы предназначены для хранения данных пользователей, а другие необходимы для хранения системной информации, например, страницы транзакций и инвентаризации страниц (более подробная информация о страницах базы данных https://ib-aid.com/en/articles/database-physical-structure-interbase-and-firebird/[доступна здесь]).

При шифровании базы данных Firebird шифруются только страницы с пользовательскими данными: страницы данных, индексов, генераторов и BLOB-объектов.

.Шифрование применяется только к страницам базы данных, содержащим данные пользователей
image::2_firebird_encrypted_pages.png[]

Обратите внимание, что метаданные базы данных (хранимые процедуры, таблицы, представления, имена триггеров, генераторов и т. д.) не отличаются от "`данных пользователей`" в той части механизма, которая отвечает за шифрование, и они шифруются.

Почему системные страницы не шифруются? В основном, по соображениям производительности и потому, что они не содержат конфиденциальных данных, требующих защиты.

Заголовочная страница базы данных не шифруется, поскольку содержит информацию, необходимую для шифрования (например, имя ключа).

== Когда происходит шифрование страниц данных?

Когда пользователь выполняет запрос SELECT к зашифрованной базе данных, данные считываются из зашифрованного файла, но поступают в приложение с результирующим набором в незашифрованном виде.

Рассмотрим подробности этого процесса:

.Когда происходит шифрование страниц базы данных?
image::3_when_pages_encrypted.png[]

Обычно процесс начинается с серии чтений страниц базы данных из файла базы данных, которые кэшируются в файловом кэше операционной системы.

Firebird также можно настроить на обход файлового кэша и использование только собственного кэша, но по умолчанию используется файловый кэш.

После этого Firebird считывает страницы и помещает их в кэш страниц Firebird (его размер определяется параметром `DefaultDBCachePages` в `firebird.conf` и/или `databases.conf` или в заголовочной странице базы данных).

Затем страницы из кэша выбираются в результирующий набор конкретного SQL-запроса (`SELECT` в нашем примере).

Подробности показаны на рисунке ниже:

.Между кэшем Firebird и файловым кэшем операционной системы происходит шифрование страниц
image::4_pages_encrypted_between_caches.png[]

Таким образом, страницы базы данных зашифрованы в файловом кэше операционной системы, но поступают в кэш страниц Firebird в незашифрованном виде, и наоборот.

[IMPORTANT]
====
Шифрование базы данных защищает данные на диске: файл базы данных, его копии и зашифрованные резервные копии. Оно не шифрует данные в памяти сервера и данные, передаваемые по сети. Для защиты сетевого трафика используйте шифрование протокола (`WireCrypt` в `firebird.conf`).
====

Часть программного обеспечения Firebird, отвечающая за шифрование/дешифрование, называется "`плагином шифрования`". Поскольку большинство реализаций плагинов (известных авторам) называются `DbCrypt`, мы будем называть его `DbCrypt`.

На рисунке ниже вы можете увидеть варианты для Windows (`DbCrypt.dll`) и Linux (`libDbCrypt.so`):

=== Алгоритм шифрования

Плагин `DbCrypt` от IBSurgeon шифрует страницы алгоритмом AES. Длина ключа определяет вариант алгоритма:

[cols="1,1", options="header"]
|===
| Длина ключа | Алгоритм
| 16 байт | AES-128
| 24 байта | AES-192
| 32 байта | AES-256 (рекомендуется)
|===

Утилита `aesKeyGen` (см. <<fbcrypt-keygen>>) создаёт ключи длиной 32 байта.

Криптографические функции плагин берёт из библиотеки OpenSSL (`libcrypto`). Эта библиотека должна быть доступна и серверу, и клиентским утилитам (см. <<fbcrypt-config-openssl>>).

== Управление ключами

Если вы достаточно долго будете смотреть на предыдущую картинку, довольно быстро возникнет следующий вопрос: как `DbCrypt` получает правильный ключ для шифрования/расшифровки страниц базы данных?

Ответ -- существует другой плагин для управления ключами.

Обычно для управления ключами используется плагин под названием `KeyHolder`, который служит средством хранения/управления ключами для плагина шифрования (`DbCrypt`). `KeyHolder` реализует интерфейс управления ключами, используемый `DbCrypt`.

[NOTE]
====
Также (в случае соответствующего написания кода плагина шифрования) он способен самостоятельно загружать ключ, например с внешнего flash USB, но в данном документе этот вариант не рассматривается.
====

.DbCrypt и KeyHolder
image::7_dbcrypt_and_keyholder.png[]

*Что означает "`управление ключами`"?*

В простейшем случае `KeyHolder` считывает ключи из файла на сервере и передаёт их плагину `DbCrypt`. В плагинах IBSurgeon это текстовый файл `KeyHolder.conf` в каталоге `plugins`.

Файл ключей может содержать несколько ключей, хранящихся для удобства в виде именованного списка, и может выглядеть следующим образом (пример ниже взят из фреймворка плагинов шифрования IBSurgeon):

[listing]
----
Key=Red 0xec,0xa1,0x52,0xf6,0x4d,0x27,0xda,0x93,0x53,0xe5,0x48,0x86,0xb9,0x7d,0xe2,0x8f,0x3b,0xfa,0xb7,0x91,0x22,0x5b,0x59,0x15,0x82,0x35,0xf5,0x30,0x1f,0x04,0xdc,0x75,
Key=Green 0xab,0xd7,0x34,0x63,0xae,0x19,0x52,0x00,0xb8,0x84,0xa3,0x44,0xbd,0x11,0x9f,0x72,0xe0,0x04,0x68,0x4f,0xc4,0x89,0x3b,0x20,0x8d,0x2a,0xa7,0x07,0x32,0x3b,0x5e,0x74,
----

Когда база данных зашифрована, её заголовок (нулевая страница) остаётся незашифрованным и хранит в том числе информацию о плагине шифрования и имени ключа. Заголовок защищён зашифрованными хешами, предотвращающими попытки расшифровать БД с помощью изменения его состояния. Эту информацию можно просмотреть с помощью команды `gstat -h databasename`:

=== Выбор правильного ключа

Часто разработчики задают вопрос: "`Как плагин определяет, какой ключ для какой базы данных?`" Ответ довольно прост: по имени ключа, которое хранится на странице заголовка базы данных.

[NOTE]
====
Плагин `KeyHolder` сравнивает имена ключей без учёта регистра. Имена `Red`, `RED` и `red` обозначают один и тот же ключ. Если имя ключа в операторе `ALTER DATABASE ENCRYPT` записано без кавычек, Firebird сохраняет его в заголовке в верхнем регистре (`RED`).
====

Реже, но всё же важный вопрос: что если имя ключа совпадает с именем, указанным в заголовке, но значение ключа отличается? Firebird защищается от этого двумя проверками:

* *Key hash.* При шифровании базы данных Firebird просит плагин `DbCrypt` зашифровать тестовую последовательность (`0123456789ABCDEF`) и сохраняет хеш результата в заголовке. При каждом подключении Firebird повторяет эту операцию с полученным ключом и сравнивает хеш с сохранённым. Если значения отличаются, подключение завершается ошибкой, и ни одна страница не читается с неправильным ключом.

* *Crypt checksum.* Поля заголовка, которые относятся к шифрованию (признаки "`зашифрована`" и "`идёт шифрование`", номер текущей страницы шифрования, имя плагина, имя ключа и хеш ключа), зашифрованы ключом базы данных и сохранены как контрольная сумма. Изменить эти поля без ключа и не нарушить контрольную сумму нельзя.

=== Откуда KeyHolder получает ключи

Плагин `KeyHolder` от IBSurgeon может получить ключи из трёх источников:

[cols="2,3,3", options="header"]
|===
| Источник | Как настроить | Когда использовать
| Клиентское приложение (по сети)
| Приложение передаёт ключ при подключении: через `fbcrypt`, `KeySource`, `KeyHolderStdin` или свойство драйвера. См. <<fbcrypt-client-app>>.
| Рабочая система. Ключа на сервере нет.

| Библиотека `KeySource` на сервере
| Библиотека `KeySource.dll` / `libKeySource.so` в каталоге библиотек Firebird. См. <<fbcrypt-keysource>>.
| Ключ нужен серверу без участия клиентов, но не должен лежать в текстовом файле.

| Файл `plugins/KeyHolder.conf`
| Строки `Key=<имя> <значение>` или `Password=<имя> <пароль>`. См. <<fbcrypt-config-keyholder>>.
| Отладка, тестирование, первичное шифрование.
|===

Если клиент передал ключ с тем же именем, что и ключ из файла `KeyHolder.conf`, используется ключ клиента.

Подход, при котором ключи находятся на сервере, прост и удобен для отладки, тестирования производительности и т. д., поскольку он реализует шифрование прозрачным образом: то есть клиентские приложения и инструменты разработчиков не знают, что база данных зашифрована.

Однако в реальности необходимо ограничить доступ приложений к базе данных: только клиентское приложение, имеющее ключ, должно иметь возможность подключаться к зашифрованной базе данных.

Для этого плагин `KeyHolder` позволяет получить ключ из клиентского приложения (которое обычно находится на другом компьютере) по сетевому протоколу Firebird.

[IMPORTANT]
====
Плагин `KeyHolder` от IBSurgeon не делится ключами между подключениями. Если ключа на сервере нет, *каждое* подключение должно само передать правильный ключ. Подключение без ключа получит ошибку, даже если в это время с базой данных работает другое подключение с ключом.

Это относится и к служебным подключениям: `gbak`, `gfix`, `nbackup`, `isql`, инструментам администратора, репликации. См. <<fbcrypt-utils>>.
====

== Как защитить передачу ключей?

Возможно, нам потребуется защитить базу данных в ситуации, когда клиент решает получить прямой доступ к зашифрованной базе данных, минуя авторизованные приложения (многие поставщики хотят ограничить доступ к данным, разрешив только доступ из специального приложения).

Это эквивалентно ситуации, когда злоумышленник имеет доступ к серверу, но не имеет ключей.

Рассмотрим следующие сценарии атаки для перехвата ключей на стороне сервера:

. Когда злоумышленник создает поддельный плагин шифрования (`DBCrypt.dll`) и размещает его на сервере, и когда `KeyHolder` передает ключ, поддельный `DbCrypt` делает дамп ключа:
+

image::11_attack_with_fake_dbcrypt.png[]

. Когда злоумышленник создает поддельный файл `firebird.exe` и делает с его помощью дамп:
+
.Атака с помощью поддельного firebird.exe
image::12_attack_with_fake_firebird.png[]

Для защиты от подобных атак, качественная реализация плагинов шифрования и управления ключами должна обеспечивать защиту обмена ключами.

Обмен ключами можно защитить с помощью асимметричного шифрования с использованием пары открытого/закрытого ключей.

Эти ключи генерируются в процессе сборки и встраиваются для конкретной пары плагинов шифрования и управления ключами. Для наилучшей защиты необходимо использовать специально созданные пары `DbCrypt`/`KeyHolder`.

image::13_key_exchange.png[]

В плагинах IBSurgeon ключ проходит два участка: от клиентского приложения к `KeyHolder` и от `KeyHolder` к `DbCrypt`. На каждом участке используется один и тот же протокол, но своя встроенная пара ключей RSA. Обозначим стороны как "`получатель`" (тот, кому нужен ключ базы данных) и "`отправитель`" (тот, у кого этот ключ есть):

[listing]
----
Получатель → Отправитель:
	Запрос на начало обмена
Отправитель → Получатель:
	Случайная последовательность (новая для каждого обмена)
Получатель:
	Создаёт одноразовую пару ключей RSA
	Подписывает встроенным закрытым ключом
		(случайную последовательность + одноразовый открытый ключ)
	Отправляет одноразовый открытый ключ и подпись
Отправитель:
	Проверяет подпись встроенным открытым ключом
	Если подпись неверна - ключ не отправляет
	Шифрует ключи базы данных одноразовым открытым ключом
	Отправляет зашифрованные ключи (при необходимости - по частям)
Получатель:
	Расшифровывает ключи одноразовым закрытым ключом
	Готов к работе
----

Такой обмен даёт следующие свойства:

* Ключ базы данных никогда не передаётся в открытом виде.
* Отправитель отдаёт ключ только "`своему`" получателю: поддельный плагин без встроенного закрытого ключа не сможет создать правильную подпись.
* Перехваченный обмен нельзя повторить: случайная последовательность и одноразовая пара RSA новые для каждого подключения.

Реализация защиты обмена ключами в плагине IBSurgeon обеспечивает также защиту данных при передаче по недружественной глобальной сети, в том числе в тех случаях когда ключ должен быть передан по каналу, ещё не готовому шифровать все данные штатным для Firebird образом. Такая ситуация возникает при использовании self security database.

[IMPORTANT]
====
Обратите внимание, что шифрование и корректность передаваемых ключей зависят от реализации плагина; движок Firebird предоставляет только базовую низкоуровневую услугу передачи: "`отправить N байтов из этого экземпляра плагина в экземпляр парного плагина`".
====

[NOTE]
====
Клиентская библиотека `fbcrypt`, плагины `KeyHolder`, `KeyHolderStdin` и `DbCrypt` должны быть из одного пакета. Библиотеки из разных сборок могут иметь разные встроенные пары ключей и в этом случае не смогут обменяться ключом.
====

[discrete]
== Краткое описание серверной части шифрования

* Шифрование/дешифрование выполняется плагином шифрования базы данных (`DbCrypt`) постранично, во время обмена данными между файловым кэшем операционной системы и кэшем страниц Firebird.

* Шифруются страницы данных, индексов, BLOB и генераторов. Заголовок и служебные страницы не шифруются.

* Ключами управляет плагин `KeyHolder`. Он получает ключи от клиентского приложения, из библиотеки `KeySource` или из файла `KeyHolder.conf`.

* Ключ передаётся между приложением, `KeyHolder` и `DbCrypt` только в зашифрованном виде.

* Если ключа на сервере нет, его должно передать каждое подключение.

Теперь давайте разберемся, как клиентские приложения работают с зашифрованными базами данных.
