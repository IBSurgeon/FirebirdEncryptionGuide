[[fbcrypt-usage]]
= Encryption, decryption and key change

This chapter describes the main operations with an encrypted database.

== Before you start

Check the following:

. You made a backup of the database. Do the first tests only on a copy.
. The plugin is installed, the license file `DbCrypt.conf` is in the `plugins` folder (see <<fbcrypt-install>>).
. The parameter `KeyHolderPlugin = KeyHolder` is set in `firebird.conf` or in `databases.conf`.
. The key is created, and its copy is kept outside the server (see <<fbcrypt-keygen>>).
. The key is available to the server. There are three ways:
** temporarily write the key to the `plugins/KeyHolder.conf` file;
** send the key from the client with the `isql` utility and the `KeyHolderStdin` plugin (see <<fbcrypt-utils>>);
** run the statement with the `isql` utility from the client folder that contains the `KeySource` library (see <<fbcrypt-keysource>>). The client `KeyHolder` plugin sends the key to the server, a file on the server is not necessary.

If the client sends the key, connect over TCP/IP (`localhost:` or `inet://`), not with a local path without a server name and not over XNET. See <<fbcrypt-connection-kinds>>.

[[fbcrypt-connection-kinds]]
== Connection kinds

The Firebird server asks the client for the key only on a TCP/IP connection. On an XNET connection the key must be on the server.

[cols="3,2,2", options="header"]
|===
| Connection | Key in the file `KeyHolder.conf` on the server | The client sends the key
| TCP/IP: `server:database`, `server/port:database`, `inet://server:port/database`
| works
| works

| XNET: `xnet://database`. Windows only, the client and the server are on the same computer
| works
| does not work, error `Key not set`
|===

The client sends the key in each of these methods: `fbcrypt`, `KeySource`, `KeyHolderStdin`, the switch `-KeyHolder` of the utilities. The Firebird server sets this rule, so it is the same for all methods.

* *Local path without a server name (Windows).* The result depends on the client parameter `Providers`. The provider `Engine13` (in 3.0: `Engine12`) opens the file inside the client process: this is embedded mode, there is no network, and the plugin `KeyHolder` of this process gets the key. The provider `Loopback` on Windows tries XNET first, and the client key is not sent. With only `Remote` in `Providers`, the connection fails with the error `unavailable database`. Write the server name, and the result does not depend on the settings.
* *Wire encryption.* On XNET the data goes through the shared memory of the computer. The `WireCrypt` plugins do not encrypt it: `WIRE_ENCRYPTED = FALSE`. This is the standard behaviour of Firebird.
* *WNET (named pipes).* It exists only in Firebird 3.0 and 4.0. Not tested. By the source code of the server, the rule is the same as for XNET.
* *XNET name.* If the server has the parameter `IpcName`, the client `firebird.conf` needs the same value.

Tested on 24.11.2026 with Firebird 3.0.14, 4.0.7 and 5.0.4 for Windows: `isql` with the `KeySource` library, and `gbak` (on 4.0 and 5.0 with the switch `-KeyHolder KeyHolder`).

== Database encryption

[source,sql]
----
ALTER DATABASE ENCRYPT WITH "DbCrypt" KEY Red;
COMMIT;
----

[cols="1,3", options="header"]
|===
| Element | Comment
| `"DbCrypt"`
| The name of the encryption plugin. On Linux the name is case sensitive, so write it in double quotes. On Windows the quotes are optional.

| `Red`
| The key name. Without quotes, the name is stored in upper case (`RED`). The `KeyHolder` plugin compares names without case sensitivity.
|===

The statement only starts the encryption. A background thread of the server encrypts the pages:

* The encryption continues while there is at least one connection to the database. For a large database, keep a connection open until the encryption is complete.
* You can work with the database during the encryption.
* If the server was stopped, the encryption continues at the next connection with the key.

How to check that the encryption is complete is described in <<fbcrypt-monitoring>>.

[WARNING]
====
After the encryption, run `gstat -h`: the `Attributes` line must contain the word `encrypted`.

The `ALTER DATABASE ENCRYPT` statement can complete without an error and not encrypt the database. This occurs on Firebird 3.0, 4.0 and 5.0 when the key is set in the `KeyHolder.conf` file as a pass phrase with curly brackets. The allowed characters of the phrase are listed in <<fbcrypt-keygen-password>>.
====

After the encryption is complete:

. If the key was written to `plugins/KeyHolder.conf` only for the encryption, delete or rename this file and restart Firebird. The server works without the `KeyHolder.conf` file: it is necessary only for the plugin parameters (see <<fbcrypt-config-keyholder>>).
. Check that a connection without the key is not possible.
. Check that the applications and the backup work.

== Database decryption

[source,sql]
----
ALTER DATABASE DECRYPT;
COMMIT;
----

Decryption also runs in a background thread. Do not delete the key and the `KeyHolderPlugin` parameter while `gstat -h` shows the `encrypted` attribute.

== Key change

Firebird cannot replace the key of an encrypted database with one command. An attempt to run `ALTER DATABASE ENCRYPT` for an already encrypted database fails with an error. There are two ways to change the key.

*Method 1. Decrypt and encrypt again.*

. Run `ALTER DATABASE DECRYPT` and wait until it is complete.
. Run `ALTER DATABASE ENCRYPT WITH "DbCrypt" KEY <new name>`.

Between the steps, the database is on the disk in plain form. Both operations read and write all pages.

*Method 2. Backup and restore.*

. Make a backup with the `gbak` utility.
. Restore it to a new database with the parameter `-KEYNAME <new name>`.

See <<fbcrypt-utils-gbak>>.

[TIP]
====
Give the new key a new name. Then the key name in the header (`gstat -h`) always shows which key encrypted the database or its copy.
====

== Who can encrypt the database

The `ALTER DATABASE ENCRYPT` and `ALTER DATABASE DECRYPT` statements can be run by the database owner, by an administrator (`SYSDBA`, the `RDB$ADMIN` role) or by a user with the `ALTER DATABASE` privilege.

Encryption does not replace access control. A user who connected with the correct key sees the data according to the SQL privileges of this user.
